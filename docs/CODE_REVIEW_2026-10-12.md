# 总体代码审查与整改记录

审查日期：2026-10-12

## 审查结论

当前项目能够完成 TypeScript 检查、生产构建和冒烟测试，公开站与管理端在桌面端、平板端、手机端以及浅色、深色主题下均可正常渲染。

但是，“能够运行”不等于“已经达到生产验收标准”。以下问题在修复并重新验收前，统一视为待整改项。

## 整改结果（2026-10-12）

本记录中的 P0 项已全部完成并通过 TypeScript、生产构建、接口冒烟和真实迁移恢复演练。P1 中的公开首页、公开/管理入口、统一 CRUD、设置分区、维护文案、后台搜索、管理员入口、品牌 Logo 和静态站自定义 404 已完成。

系统更新已完成可替换更新源、版本检测、SHA-256、更新前完整备份、更新包暂存和外部安全执行器接口。由于 GitHub 仓库与生产进程托管方式尚未提供，真实 Releases 下载、服务重启和故障回滚演练仍属于外部接入项，界面会明确显示“更新源未配置”，不会伪装成已更新。

完整迁移备份已经替代旧 JSON 恢复：归档包含数据库、静态网站发布历史、品牌资源以及本地或 S3 安装包内容；生成与恢复均使用流式处理，恢复前自动创建回滚备份，并验证安全路径、文件大小和 SHA-256。

## 用户确认的总体整改范围

1. 公开首页目前过于简陋，更接近设计原型，不符合专业公开官网标准。
2. 公开站与管理端虽然已经拆分构建，但公开站仍保留管理登录入口，访问边界不彻底。
3. API 必须保留为前后端通信边界，但默认不再单独暴露 API 域名，避免增加 CORS、Cookie、证书和部署复杂度。
4. 管理后台各模块的新增、编辑、启停、归档和删除能力不统一，部分模块只有新增或只有后端删除接口。
5. 系统设置虽然划分为五类，右侧内容却全部铺开，属于只有视觉分类、没有真正分区。
6. 管理后台需要增加系统版本检测和安全的一键更新能力。
7. 备份必须升级为可下载、可上传、可跨服务器直接恢复的完整迁移备份，不能只导出数据库 JSON。

## P0：生产上线前必须修复

1. **禁止未验证域名直接启用**
   - 当前域名更新接口接受 `active` 状态，但没有同时检查 `dns_status`。
   - 前端也允许将非启用域名直接切换为启用。
   - 整改：服务端强制验证 DNS 所有权；前端仅作为交互提示，不能代替服务端校验。

2. **删除 S3 安装包时同步删除远端对象**
   - 当前删除流程只删除数据库记录和本地文件路径。
   - S3 模式下会遗留远端对象并持续产生存储费用。
   - 整改：根据存储提供方调用对象删除接口，并在删除失败时保留数据库记录或进入待清理状态。

3. **补全 S3 直传 SHA-256 校验**
   - 当前 S3 完成校验依赖 `x-amz-meta-sha256`，上传流程没有可靠写入该元数据。
   - 整改：浏览器分片计算哈希并在完成接口提交，服务端验证对象大小、分片和哈希；不能验证时不得标记为可下载。

4. **建立独立的软件版本模型**
   - 当前“版本管理”直接使用安装包记录；同一版本的多个平台安装包会成为多个版本。
   - 编辑历史安装包可能覆盖软件当前版本。
   - 整改：增加 release/version 实体，由一个版本关联多个平台安装包，并独立维护正式版、测试版、推荐版和当前版本状态。

5. **补全跳转规则安全校验**
   - 当前缺少生效时间、失效时间、规则冲突检测和循环跳转检测。
   - 整改：保存与执行阶段都进行冲突、循环和有效期校验，并为规则提供编辑、停用和删除入口。

6. **下载成功后再统计**
   - 当前在确认本地文件存在或成功生成对象存储地址之前就递增下载次数。
   - 整改：本地文件完成响应准备、云端下载地址生成成功后再记录下载事件；失败请求不得进入成功统计。

7. **生产环境禁止大文件本地中转**
   - 当前生产环境配置本地存储时只输出警告。
   - 整改：生产模式默认拒绝本地安装包存储，只有显式的开发或受控测试开关可以放行。

## P1：专业版完整性整改

1. 维护模式填写的自定义说明没有进入最终维护页面，运行时仍使用固定模板。
2. 备份导入只更新数据库中已经存在的 ID，无法恢复被删除的记录，不属于完整灾备恢复。
3. 全局搜索框、管理员资料按钮和“忘记密码”入口目前没有实际功能。
4. 跳转规则卡片的更多按钮没有行为，部分纯图标按钮缺少可访问名称。
5. Logo 文件上传仍处于禁用状态。
6. 软件删除接口与管理界面能力不一致，需要明确软删除、归档或彻底删除策略。
7. 静态网站缺少可配置的自定义 404 页面与完整资源管理界面。
8. 公开首页缺少真实产品、最新版本、公告、使用场景、品牌介绍、安全承诺、服务状态和完整页脚。
9. 公开首页仍存在“管理控制台”“开始构建”等内部管理导向入口，应从公开构建中移除。
10. 域名缺少完整资料编辑入口；跳转规则缺少编辑、启停和删除；版本缺少独立生命周期管理。
11. 删除、归档和更多操作的图标语义不统一，部分删除操作错误使用省略号图标。
12. 系统设置五个分类没有真正切换内容，导致页面过长、手机端滚动繁重且分类导航失去意义。

## 系统设置整改要求

当前五类设置必须改成真正的分区界面：

- 桌面端使用左侧分类导航，只渲染当前选中的分类。
- 手机端使用横向标签或下拉选择，不能把全部设置连续铺开。
- 每个分类独立加载、保存并显示错误状态。
- 支持使用 URL 参数直接进入指定分类，例如 `/admin/settings?section=storage`。
- 切换分类时如存在未保存修改，必须提示管理员。
- 分类存在配置异常时，在导航项展示状态或警告标记。
- 系统更新和完整迁移备份归入独立的“系统维护”分类，不继续堆放在普通品牌设置中。

## 系统在线更新要求

管理后台需要提供完整的系统更新中心：

1. 显示当前版本、构建时间和更新通道。
2. 支持手动检测最新版本，并展示版本号、发布日期和更新说明。
3. 管理员确认后可以执行更新，但更新前必须自动创建完整迁移备份。
4. 更新包必须验证 SHA-256；正式发布建议同时验证数字签名。
5. 更新必须先解压到暂存目录，完成兼容性检查和数据库迁移检查后再切换版本。
6. 更新期间进入维护状态，并保存可恢复的旧版本。
7. 更新后执行健康检查；失败时自动回滚程序文件和数据库。
8. 所有检测、下载、安装、重启和回滚操作必须进入审计日志。
9. GitHub 仓库提供后，对接 GitHub Releases 获取稳定版本和发布包；仓库提供前先保持可替换的更新源接口。
10. 一键更新依赖明确的进程托管方式，例如 systemd、PM2、Docker 或平台部署器；应用进程不能在没有外部守护的情况下假装完成自更新和重启。

## 完整迁移备份要求

完整备份必须是一个带格式版本的可迁移归档，而不是只包含数据库记录：

- SQLite 数据库一致性快照；
- 域名、跳转规则、公告、软件、版本、安装包和审计配置；
- 静态网站源文件、已发布版本及历史版本；
- 本地安装包、Logo、品牌资源和其他上传文件；
- S3 模式下的对象清单以及可选的对象内容完整导出；
- 运行所需的非敏感配置、备份格式版本、系统版本和迁移说明；
- 每个文件的大小、SHA-256、总文件数和总大小；
- 数据库结构版本与最低兼容系统版本。

恢复流程必须满足：

1. 管理员下载一个完整备份归档，在新服务器上传同一归档即可进入恢复流程。
2. 上传后先检查格式、哈希、文件完整性、磁盘空间和版本兼容性，校验失败不得修改当前系统。
3. 恢复前自动创建当前系统快照，在暂存目录完成解包与验证后再原子切换。
4. 恢复失败自动回滚，不能留下数据库已恢复但文件未恢复的半完成状态。
5. 大型备份必须使用流式生成、流式下载、分片上传和断点续传，不能整包载入服务器内存。
6. 敏感密钥默认不明文写入归档；需要携带时必须使用管理员提供的密码加密，并在新服务器进行明确确认。
7. 对象存储迁移需要同时支持“备份包内包含对象”和“源存储到目标存储服务端复制”两种模式。

## API 与部署架构决定

API 是前端与后端之间的通信边界，但不要求必须使用独立的公网域名，也不要求拆成独立仓库。

本项目推荐采用：**单仓库、两个用户入口、一个后端服务、同源 API 代理**。

```text
www.example.com
├── 公开站静态文件
└── /api/public/*  ──反向代理──┐
                              │
admin.example.com             ├── Node API / 数据库 / 对象存储签名
├── 管理端静态文件             │
└── /api/*         ──反向代理──┘
```

约束：

- 公开站不显示任何管理端登录入口，也不打包管理端代码。
- 管理端使用独立子域名，根路径即登录页或受保护的管理页面。
- 浏览器始终请求当前域名下的 `/api`，由 Nginx、Caddy 或负载均衡转发到同一个 Node 后端。
- 默认不公开 `api.example.com`，减少 CORS、Cookie、证书和环境变量配置复杂度。
- 后端代码、鉴权和接口权限仍然保持严格边界；“同源访问”不代表取消 API 层。
- 自定义跳转域名和静态网站域名继续由边缘代理转发到同一个域名运行时服务。

独立 API 域名仅在以下情况再启用：需要提供第三方开放 API、移动客户端直接调用、多后端服务拆分、独立 API 网关或跨区域部署。

## 建议整改顺序

1. 修复域名启用、对象删除、哈希校验和下载统计等数据安全问题。
2. 建立独立版本模型，补全跳转规则和后台统一 CRUD 生命周期。
3. 重做专业公开首页，移除公开站全部管理入口。
4. 保留公开站与管理端两个入口，将各自 `/api` 反向代理到同一后端，不单独暴露 API 域名。
5. 将系统设置改成真正的分类切换，并补全无效 UI 操作、无障碍和 Logo 资源模型。
6. 实现完整迁移备份、校验、原子恢复和失败回滚。
7. 在完整备份能力稳定后实现版本检测、安全更新、健康检查和自动回滚。
8. GitHub 仓库提供后接入 Releases 更新源并完成真实更新演练。
9. 重新执行代码检查、生产构建、接口测试、备份恢复演练、更新回滚演练和多端 UI 验收。
